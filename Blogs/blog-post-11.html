The database that disappeared on every deploy

Article

An incident report for Khoebo. I assumed my app server was a persistent VPS, but on Render it was a disposable container, and a handful of early users paid for that assumption. This is what happened, what I changed, and what I am sorry for. Live app: khoebo.onrender.com. Source: github.com/DevnProgg/khoebo.

The root cause: I thought I had a server

Before Render, I hosted on a VPS. On a VPS, if your app writes khoebo.db into its own directory, that file is still there tomorrow. It survives a process restart, a reboot and a redeploy, because the machine and its disk are yours. That model was so familiar that I carried it across without questioning it.

Render does not give you that machine. A web service runs in a container with an ephemeral filesystem. When the process restarts, whether because of an auto deploy, a restart or a crash, the container and everything inside it goes away. I did not know that at the time. I genuinely believed I was running a small persistent server in the cloud, and so a local SQLite file felt like a perfectly reasonable choice "for now".

It was a trap created by the gap between the platform I came from and the platform I had moved to. The setup looked identical from the outside: a URL, a deployed app, a database file that existed. The difference was underneath it, and it was the one thing that mattered.

What happened

Khoebo's settings had a default database URL: sqlite:///./khoebo.db. That is a perfectly reasonable default for local development and for the test suite. It was also the URL the deployed service was using, because the environment variable that should have pointed at PostgreSQL was never updated. Had I understood the hosting model, that misconfiguration would have been obvious instead of invisible.

The SQLite file lived inside the app directory, so every new container got a fresh, empty database. The service then came back looking completely healthy. There was no error page and no failed health check. The process was up, the endpoints answered, and the schema existed. The rows from yesterday simply did not.

Why I did not catch it sooner

The biggest reason was the wrong mental model. I was not looking for this failure because, in my head, local files on a server persist. Everything else followed from that.

The app was also very new and adoption was not exactly booming. At the time there were about three users. That is not an excuse, but it is the reason the symptom went unnoticed for a while: nobody was leaning on the data hard enough to notice it had gone.

The tests would not have caught it either. They run against in-memory SQLite, which is created and discarded for each test run by design. Persistence across a process restart is not a property that kind of test can check.

There were production guardrails, but they checked the wrong things. The startup validation rejected a weak secret key and refused automatic table creation in production. Nothing checked the database URL itself, and nothing checked what the hosting platform guaranteed about disk. A local file path could pass every check and still be the production database. I was watching whether the app was up, not whether the data was still there.

The impact

A small number of accounts lost their products, sales and records. I could not recover that data. Once the container is gone, a SQLite file inside it is gone too.

The blast radius was small because the app was small. That does not make it harmless. A few people had trusted a brand new tool with information about their business, and I let them down. To those users, my sincere apologies. You did nothing wrong, and I am sorry I was not careful enough with your data.

The fix: separate the data from the server

The short-term fix was to make sure the database no longer shared a lifecycle with the application server. I moved Khoebo to PostgreSQL running off to the side, so an application restart, a crash or a bad deploy cannot touch the data. App servers are disposable now. The database is not.

For this small app I did not want to operate a database myself, handle its security, or become the person who gets paged at 2am about replication. That is a legitimate reason to use a managed service, so I moved the database to Supabase. It gave Khoebo a PostgreSQL database with backups and access control handled by people whose job that is.

The application code barely changed. The settings already normalise postgresql:// to postgresql+psycopg:// and add sslmode=require for Supabase hosts, so the real work was configuration. There was one more lesson in that: my first connection attempt used Supabase's direct connection string and failed with Network is unreachable, because that endpoint is IPv6-only and Render is IPv4-only. Switching to the session pooler connection string, which is IPv4 on every plan, resolved it.

The incident was not closed by recovering the data. It was closed by removing the failure mode.

What changed afterwards

Backups are now a first-class requirement in this project, not a deployment detail I will get round to. The managed provider handles scheduled backups, and my responsibility is to know the retention window and actually test a restore. A backup you have never restored is a hope, not a backup.

I also treat the two questions separately: "is the app up?" and "is the data still there?". A green health check only answers the first one. Before any deploy I now confirm the database URL points at the managed instance, and the plan is to make that check automatic so that a missing or local URL fails the deploy instead of quietly succeeding.

The lesson

The mistake was not really about SQLite. It was about carrying assumptions from one hosting model into another. A VPS gives you a machine and a disk; a container platform gives you a process and a fresh filesystem. If you do not know which one you are running, you cannot reason about where your data lives.

Ephemeral compute plus a local database file is not a database; it is a scratchpad. A default that is harmless in development becomes dangerous in production when the deployment model changes underneath it. And a small user count changes the size of an incident, not its nature.

I am grateful that the people affected were patient with a very early product. The current iteration of Khoebo is built around making sure the data outlives the server, and that it can be brought back when something goes wrong. That is the promise I should have made from the start.
