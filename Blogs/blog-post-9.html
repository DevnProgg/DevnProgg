The hard part isn't making a payment request

Article

Four commits, eight transaction types, and the quiet infrastructure that makes an M-Pesa SDK worth using. Source code: github.com/DevnProgg/mpesa-sdk.

Why I built it

I started building this because integrating with M-Pesa can mean dealing with sessions, encryption, API contexts, headers, retries, errors, and a lot of documentation. Even the existing Python library still left me writing much of the payment logic myself.

So I decided to build the abstraction I wanted. This is the experience I was after: focus on the transaction, not the API internals.

import asyncio
import MpesaSDK as mp

provider = mp.config({
    "market": mp.markets.LESOTHO,
    "api-key": "...",
    "public-key": "..."
})

async def main():
    response = await provider.initialize_transaction(
        type=mp.transactions.C2B_SINGLE_STAGE,
        payload={
            "amount": "10.00",
            "customer_msisdn": "26658123456",
            "service_provider_code": "000000",
            "reference": "T1234C",
            "description": "Shoes"
        }
    )
    store(response.audit.log)

asyncio.run(main())

Borrowing from Omarchy's Omakase philosophy: I make the tough decisions so the developer doesn't have to. The SDK handles retries, async processing, Celery and Redis workers, audit logging, idempotency, transaction tracing, session management, and reconciliation.

The hard part isn't making a payment request. It's making payment processing reliable.

Four commits in two weeks

The first commit was a C2B-only SDK. Everything else came after it, one feature and one pull request at a time.

CommitVersionWhat landed
First0.1.0C2B single stage, plus the reliability skeleton underneath it
Second0.2.0B2C payouts: the business pays the customer
Third0.3.0B2B transfers between two shortcodes
Fourth0.4.0Reversals: full and partial refunds, tied to the original transaction

Each feature follows the same shape: a transaction type, a validated payload, an operation registration, a callback path where the API supports one, and tests that exercise the real wire format. There are now eight combinations: C2B, B2C, B2B and reversal, each with a synchronous and an asynchronous mode.

Here's to making payment processing easy and care free.

Refunds are where payment code gets scary

The fourth commit was the one I was most careful with. A payment can fail in a dozen boring ways. A refund can fail in all of those ways and also take money back twice.

Reversals now join C2B, B2C and B2B in the same pipeline. You undo a payment in full or in part with one call. Leave the amount out and the SDK omits the amount field entirely, which is what M-Pesa expects for a full reversal. You identify the original transaction by its M-Pesa transaction id, not by your own idempotency key, and the audit trail records the link as related_transaction_id so every refund stays traceable back to the payment it undoes.

The important rule: if a reversal request times out, it is never blindly retried into a second reversal. It is flagged for reconciliation instead. The same rule applies to payouts, where a blind retry is a second transfer to a customer.

What happens when the answer is "maybe"

A payment API does not only say yes or no. Sometimes it says nothing, and sometimes the network eats the answer. The SDK classifies responses before it decides whether to try again:

  • INS-0 is success. INS-1 and INS-9, timeouts, 5xx responses and ambiguous errors are retried, but marked ambiguous.
  • A 429 or a gateway 401/403 without a response body is retried with a session refresh where appropriate. Session-limit codes invalidate the cached session rather than burning through attempts.
  • INS-10 means a duplicate. It is never retried. If it arrives after an ambiguous attempt, the result is UNKNOWN, not FAILED, because the original may well have gone through.
  • Unknown result codes are terminal. Guessing is how you turn a confusing response into a double charge.

Retries use exponential back-off with jitter: roughly 5, 10 and 20 seconds by default, capped at 300 seconds. When retries run out on an ambiguous outcome, the response carries UNKNOWN and err.needs_reconciliation = True. That is an instruction to query the transaction status with the same transaction id before paying again, not an invitation to resubmit.

One key, no double charges

Every transaction gets an idempotency key, sent as input_ThirdPartyConversationID. It is also the transaction id in the audit log, and it stays exactly the same across every retry attempt. M-Pesa uses it to detect duplicates; the SDK uses it to make a retried request the same request rather than a new one.

In queue mode the Celery task id is the transaction id too, and the state travels with each retry. Workers use late acknowledgements, so a worker that dies mid-flight does not silently drop work. Credentials live in the application module and never go into a Redis message. Payload data such as amounts and MSISDNs does travel through the broker, so Redis still needs to be secured properly.

Audit first, questions later

Every call produces a JSON-safe audit.log: transaction id and type, amount and currency, who was debited and credited, the exact request body, the last API response, a UTC timestamp, and one record per attempt with its HTTP status, result code and disposition. Callbacks, completion time and the related transaction id are recorded as well. No API key or session key ever goes into it.

The README says to store the log always, and I mean it. Audit entries can contain phone numbers, so treat that table as personal data. But when a customer asks where their money went, that log is the difference between an answer and a guess.

Two ways to run it

The retry engine has one atomic unit of work: a single attempt. In inline mode, an asyncio loop sleeps between attempts. In queue mode, each attempt is a Celery task that schedules the next one. Same decisions, same idempotency key, same audit trail; you just pick whether a backing-off transaction occupies your process or not.

Queue mode also gives you wait_for() and get_result() when you need a synchronous answer from an asynchronous system, and an audit-handler callback that runs once per final outcome so you can persist the log from the worker.

For callbacks, parse_callback() checks the returned ids and result code, apply_to() closes out the stored audit entry, and ack() builds the response body M-Pesa expects. The API defines no callback signature, so verifying the sender is on you: use an IP allow-list.

Testing the scary parts

The test fake is not a string-comparison stub. It decrypts real RSA bearer tokens, so the tests exercise URL construction, session headers, encryption, retry sequencing and audit output end to end. About 247 collected tests run without network or Redis, with a real Celery plus Redis integration test available behind an environment variable.

Because the fake speaks the actual protocol, mistakes like using the wrong description key for B2C or treating an INS-6 on HTTP 401 as a session failure show up as failing tests instead of production incidents.

Still on the list

There is more to do. The Lesotho MSISDN rule has an eleven-digit exception that still needs sandbox verification. Reconciliation is a state the SDK reports, not a complete back-office job; the querying side has to be wired into whatever runs your business. Callback verification remains a deployment responsibility rather than something the SDK can enforce.

I'm building with Lesotho first, and designing it to grow from there: Ghana, Tanzania, DR Congo and Mozambique already have market definitions with their own contexts, currencies and number rules.

The point of all of this is small. A developer should be able to write one call, store one audit log, and trust that the SDK has made the unglamorous decisions correctly. Here's to making payment processing easy and care free.
