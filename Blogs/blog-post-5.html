Building a Real-Time Anti-Money Laundering Detection System in Go

I built a real-time AML transaction monitoring system from scratch, not because I work at a bank, but because I’m passionate about FinTech and wanted to understand how serious financial systems are built. What started as a small anomaly-detection experiment grew into a complete system with rules, alerts, and regulatory reporting.

Financial institutions must detect suspicious transactions without overwhelming compliance teams with false positives. My goal was to handle high transaction volumes, apply complex rules in real time, and produce audit-ready reports.

Understanding the Problem Space

I quickly learned AML isn’t just threshold checks. It requires:

  • Temporal analysis
  • Cumulative behaviour tracking
  • Velocity checks
  • Statistical deviations over time

Early prototypes also failed due to poor database performance, mostly from missing indexes.

System Architecture

The system uses a layered architecture consisting of:

  • An API layer
  • A service layer
  • A rule engine
  • Anomaly detection
  • Structuring detection
  • Alert generation
  • PostgreSQL persistence layer

Rather than adopting microservices prematurely, I implemented a modularised monolith with clean internal boundaries.

Technology Choices

Why Go?

Go was chosen for its concurrency model and strict type safety. Financial systems cannot tolerate silent type errors, and Go’s simplicity supports predictable behaviour under load.

Why PostgreSQL?

PostgreSQL provided:

  • ACID guarantees
  • Efficient time-based querying
  • Reliable transactional consistency

Some reporting-oriented data was stored using JSONB to simplify flexible compliance outputs.

Rule Engine Design

Rules are defined in JSON and validated at application startup. This allows compliance logic to evolve without redeployment while ensuring configuration errors are caught early.

This mirrors how real AML platforms separate rule configuration from execution logic.

Anomaly Detection Approach

Instead of machine learning, the system uses z-score statistical analysis.

The reason is simple: explainability matters more than novelty in regulated environments. Compliance teams and auditors must understand why alerts were generated.

Alert Lifecycle Management

Alerts follow a strict state machine:

OPEN → INVESTIGATING → ESCALATED or FALSE_POSITIVE → CLOSED

Invalid transitions are impossible by design, ensuring workflow integrity across investigations.

Engineering Challenges and Solutions

  • Slow queries
    Resolved using composite indexes.
  • Time-zone bugs
    Fixed by standardising on TIMESTAMPTZ and UTC across the system.
  • False positives in structuring detection
    Reduced by incorporating transaction context.
  • JSONB marshaling complexity in Go
    Contained using custom types.

Key Lessons Learned

  • Financial systems should be boring
  • Indexes are non-negotiable
  • Time is deceptively complex
  • Illegal states should be impossible

Final Thoughts

This project taught me that compliance engineering is about precision, not cleverness.

If I joined a fintech startup tomorrow, I’d be confident building their transaction monitoring system from scratch — and that confidence is the real result.
